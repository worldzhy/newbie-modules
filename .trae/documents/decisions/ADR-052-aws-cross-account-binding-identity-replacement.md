# ADR-052: 跨账户绑定的身份以两阶段原子替换

状态：已采纳
日期：2026-11-08
关联：ADR-002（区域作为绑定作用域）；nightwatch-backend ADR-012（生产 AWS 拓扑）

## 背景

`aws-identity` 的 `AwsCrossAccountBinding` 用一行记录表达"某个宿主 scope 与客户 AWS 建立了跨账户接入"。记录里同时承载两类信息：

- **身份**：`roleArn`、`externalId`、`awsAccountId`、`roleName`
- **作用域**：`regions`、`defaultRegion`

当前 `updateBinding` 对已存在的记录逐字段覆盖：换 `roleArn` 时沿用旧 `externalId`（`existing?.externalId || randomUUID()`），`awsAccountId`/`roleName` 以 `新值 || 旧值` 回落。这产出了两个结构性问题：

1. **混合世代**：新角色的 ARN 配旧角色的 External ID 与旧账户 ID。这条记录无法用任何一份信任策略解释——新角色的策略需要新值，旧角色的策略仍对旧值成立。
2. **未撤销的授权**：旧角色的信任策略（同一平台账户 + 同一 External ID）继续有效。身份已经换了，授权却没有任何机制失效；平台也不再持有指向旧角色的引用，无法列举、无法提示、无法回收。

同时，"更换角色"在现有实现里没有自己的时序：保存即覆盖。若保存瞬间轮换 External ID，旧角色立即不可用，而新角色可能尚未在客户账户中创建完成，运行中的项目会出现未定义长度的不可用窗口；若沿用旧值，则回到上面两个问题。

`rotate-external-id` 是另一条语义（凭据泄露后就地换值、立即失效），不应与"更换身份"共用路径。

## 候选方案

| 方案 | 数据模型 | 更换角色的时序 | 旧授权 |
|------|----------|----------------|--------|
| **A. 什么都不做** | 一行，逐字段覆盖 | 保存即生效 | 继续有效，无回收线索 |
| **B. 两阶段草案 + 原子替换（选定）** | 一行 + 可空 `pendingExternalId` | 草案期活动身份不变；探测成功后单事务替换身份值对象 | External ID 随身份轮换，旧信任策略条件不再匹配，自动失效 |
| C. 物理解绑 + 重建 | 删行后再建行 | 两步之间无有效身份 | 随 External ID 轮换失效，但产生停机窗口与记录断代 |
| D. 覆盖式 + 提示文案 | 一行，逐字段覆盖 | 保存即生效 | 继续有效，仅靠文案告知用户自行清理 |

## 决策

**方案 B**。决定性理由：

1. **身份是值对象，不是一个可编辑字段**。`roleArn`、`externalId`、`awsAccountId`、`roleName` 只有在同一世代内才有意义；只改其中任何一个都会产出无法解释的混合世代。替换必须整体发生。
2. **External ID 与角色是一对一的关联凭证**。它存在的目的是把"谁可以扮演这个角色"绑定到具体一份信任策略。沿用旧值等于让两个角色共享同一凭证，既违反一对一语义，也让旧授权继续成立。轮换是让旧授权失效的唯一机制，而不是附加的清理动作。
3. **切换前必须零停机**。草案与活动身份并存，探测成功才替换；这既保证运行中的项目不因一次配置变更而断供，也让"保存"成为一个可失败的、无副作用的探测动作。方案 C 和"保存即轮换"都必然产生未定义窗口。
4. **接入关系不可销毁**。项目与 AWS 的接入关系是持久事实（`createdAt`、审计引用、会话缓存键都依附于它），身份是它的可变值对象。替换值对象不应表现为"退出后重新接入"——方案 C 把关系本身当成可删对象，制造断代。
5. **一列就够，且首次接入天然统一**。草案阶段没有任何经过验证的 ARN，因此不持久化 `pendingRoleArn`，也就不会存入不可用凭据。`roleArn = null` 且 `externalId` 存在时，这一行本身就是"首次接入的草案"；`roleArn` 存在且 `pendingExternalId` 存在时，是"重新接入中"。同一个状态机覆盖首次接入与更换角色，不需要第二套流程。

**被否决的方案**：

- **A**：留下持续有效的旧授权与混合世代，且没有任何回收线索。
- **C**：把"接入关系"当成可销毁对象，产生停机窗口与 `createdAt` 断代；领域上让一次身份变更看起来像退出后再接入。
- **D**：把模型错误降级为文案。用户仍会在一条已知会留下未撤销授权的路径上继续操作。

## 跨宿主 / 演进检验

| 维度 | 结论 |
|------|------|
| 宿主无关性 | "草案身份 / 活动身份"与"External ID 随身份轮换"是任意宿主接入外部账户时的通用形状；不依赖 Project、Tenant 等宿主词汇，`projectId` 仍是 host scope 标量 |
| 换宿主成立性 | 单租户 SaaS 用 organization 做 scope 时，同一状态机成立：草案期旧凭据继续服务，替换后旧凭据失效 |
| 厂商边界 | `externalId`、`AssumeRole` 属于 AWS 概念，但该模块本身就是 AWS 适配器，厂商词汇留在模块自己的边界内，不向其他模块泄漏 |
| API 形状 | 新增 `POST/DELETE :scopeId/rebind`；`PUT :scopeId` 在身份变更时要求草案存在；契约使用 host scope 泛称，不出现宿主业务名 |
| 演进路径 | 若未来出现"同一 scope 多套凭据"或"凭据池"，草案列可扩展为独立表而不改变活动身份的单值语义 |

## 影响

**Schema**

- `AwsCrossAccountBinding` 增加 `pendingExternalId String?`。nightwatch 未上线，变更走 `prisma db push`，不生成 migration。

**状态机**

| 条件 | 含义 | 对外行为 |
|------|------|----------|
| `roleArn = null`，`externalId` 存在 | 首次接入的草案 | `configured = false`，向导展示 `externalId` |
| `roleArn` 存在，`pendingExternalId = null` | 已接入 | 正常提供服务 |
| `roleArn` 存在，`pendingExternalId` 存在 | 重新接入中 | 活动身份继续提供服务，向导展示 `pendingExternalId` |

**API**

- `POST :scopeId/rebind`：要求活动身份存在；无草案则生成 `pendingExternalId`，已有则幂等返回；响应同时包含活动身份与草案值。
- `DELETE :scopeId/rebind`：清空草案，回到已接入状态。
- `PUT :scopeId`：`roleArn` 与活动身份一致时只更新作用域，不探测、不轮换；不一致时必须存在草案，用草案的 External ID 探测，成功后在单事务内替换整个身份值对象、清空草案、作废旧会话；失败不落库、草案保留、活动身份不变。
- `roleArn` 已被其他 scope 绑定时返回 409，而不是让唯一约束以 500 暴露。
- `POST :scopeId/rotate-external-id` 保持原语义（就地换值、立即生效），与两阶段换角色明确区分。

**前端**

- "编辑配置"按语义拆成两个入口：修改作用域（原地保存）与更换角色（重新接入向导，展示新 External ID 与建角色指引）。
- 切换成功后提示旧角色已失效、可在 AWS 侧清理；失败时活动绑定保持可用。
- 草案态必须跨刷新稳定：重新进入页面仍停留在重新接入向导。

**审计**

- 身份替换是一个领域事实（旧身份失效、新身份生效）。若 `aws-identity` 尚无领域事件出口，宿主通过服务层订阅或审计拦截记录；事件出口的引入另议，不在本 ADR 范围。

**后续工作**

- 首次接入的 `bootstrap` 语义收敛为"创建无活动身份的草案行"，不再有第二条写路径。
- 前端 i18n 与向导文案随入口拆分同步调整。
- 旧角色清理提示只在身份替换成功时出现，未接入与仅改作用域时不出现。
